TASK ID: 4.7

TITLE: Verify payment status
STATUS: completed

OBJECTIVE:
Before any conversion (Task 4.8), authoritatively verify that a Checkout Session is actually paid using Stripe's server-side API - never trusting the webhook event body's embedded session data, and never mutating bid state in this task.

REQUIREMENT DERIVATION:
PROJECT_PLAN.md specifies only "4.7 | Verify payment status | 4.6"; combined with the non-negotiable business rule "Payment: Bid becomes valid ONLY after verified Stripe webhook confirmation", the authoritative check is defined as:
- retrieve the Checkout Session AGAIN from Stripe's server-side API by its identifier (the event body only says WHICH session to inspect)
- require retrieved session.payment_status === 'paid' ('unpaid' covers still-processing async methods; 'no_payment_required' does not apply to paid bids)
- enforce linkage consistency: client_reference_id and metadata.bid_id are both written by our own Task 4.2 code to the same bid id - absent references or a mismatch means the session cannot be safely attributed

SCOPE:
- src/lib/stripe-webhook.ts: exported verifyCheckoutSessionPaid(sessionId): Promise<PaymentVerificationResult> (typed union with stable failure reasons: session_not_paid / missing_bid_reference / reference_mismatch); retrieval failures throw descriptive errors so the endpoint answers 500 and Stripe retries
- handleCheckoutSessionCompleted now async: extracts the session reference from the event, runs verification, logs VERIFIED or NOT-verified(reason); processStripeWebhook became async and the route awaits it
- NO database access, no status mutation, no event-id ledger (4.9), no conversion (4.8), no refund/failure handling (4.10/4.11)

- HTTP semantics unchanged: 200 verified-or-unverified-but-valid (unverified simply means "no conversion will occur"), 400 invalid signature, 500 config/retrieval failures so Stripe retries
