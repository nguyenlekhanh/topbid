TASK ID: 4.3
PHASE: 4
TITLE: Success page
STATUS: completed

OBJECTIVE:
Add the /success route as the post-checkout result page. It is a UI/result page only: it never verifies payment, never calls the Stripe API, and never marks a bid paid - confirmation remains exclusively webhook territory (Tasks 4.5+).

SCOPE:
- New src/app/success/page.tsx - async server component reading searchParams (Next.js App Router conventions)
- src/lib/bids.ts - additive getBidByStripeSessionId(stripeSessionId): Promise<BidWithCategory | null> plus BidWithCategory type; anon-client lookup by stripe_session_id embedding category (id, slug, name); untrusted-input guards (blank/oversized -> null)
- src/components/SuccessState.tsx - minimal compatibility extension: new optional note prop (defaults to the original demo footnote) so real pages can show honest copy without altering Phase 1 behavior
- src/lib/checkout.ts - success_url now appends ?session_id={CHECKOUT_SESSION_ID} so Stripe injects the session identifier on redirect (compatibility fix required for 4.1's placeholder URL to function with this page); cancel_url unchanged

BEHAVIOR (authoritative data only):
- Confirmed case: bid found via session id means it is already 'paid' and publicly readable under RLS - renders amount (formatted integer-cents USD), category name, reference; copy states payment verified
- Awaiting case: unknown/unreadable/invalid session id (typical while webhook has not yet converted pending->paid) renders a neutral "Payment received / confirming" state with NO amount or category - visiting the page cannot fake or accelerate confirmation
- Untrusted URL parameter is sanitized before echo (trimmed, max 64 chars) and used only as reference text

OUT OF SCOPE:
- Webhook endpoint/signature verification/payment-status checks (4.5-4.9), marking bids paid/highest, cancel page (4.4), refunds/rate limiting, client-side data fetching libraries

PRESERVED:
- Tasks 1.1-4.2 logic untouched except the documented SuccessState note prop default and checkout success_url template (both required for this task); RLS model intact; no secret/service-role exposure (page reads via anon client)
