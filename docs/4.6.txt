WHY THE REAL-CRYPTO SUITE MATTERS (and what it caught):
The first implementation passed an options object ({tolerance:300}) as constructEvent's fourth argument; the installed SDK types define that parameter as a plain NUMBER (tolerance?: number). The object silently broke timestamp-staleness comparison - stale events were accepted with HTTP 200. The real-crypto test suite caught this immediately ("Timestamp outside the tolerance zone" now correctly rejects). Fixed by passing the numeric constant directly. This is exactly the class of bug a mocked-only suite cannot see.

TEST COVERAGE (8 new real-crypto tests; no network, no live Stripe):

- Tampered payload (signature computed over different bytes) -> 400 - proves exact-raw-payload verification
- Wrong signing secret -> 400
- Missing signature header -> 400
- Stale timestamp beyond tolerance -> 400 (replay protection active)
- Timestamp inside tolerance (now-270s vs 300s window) -> 200
- Signed non-JSON payload -> 400 (raw-body integrity through constructEvent's parse step)
- Unsupported-but-validly-signed type -> 200 ignored:true
