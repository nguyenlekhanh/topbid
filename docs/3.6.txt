TASK ID: 3.6
PHASE: 3
TITLE: Handle concurrent bids (DB locking)
STATUS: completed

OBJECTIVE:
Prevent two concurrent bid attempts for the same category from both calculating the same minimum and creating conflicting pending bids, enforced at the database level - never via an in-process JavaScript mutex, and without pretending independent Supabase queries are atomic.

SCOPE:
- New migration supabase/migrations/20260823000007_create_pending_bid_function.sql - PL/pgSQL function create_pending_bid(uuid, integer, text, text) returns jsonb containing the entire critical section
- src/lib/bids.ts - createPendingBid now invokes the RPC via the existing service-role client instead of a direct non-atomic insert; adds mapPendingBidRpcError translating bid_error:* messages into the EXISTING stable CreatePendingBidResult union (external contract unchanged)

OUT OF SCOPE:
- Duplicate transaction prevention (Task 3.7), test infrastructure (3.8), Stripe/payment flow, expiry/cleanup of abandoned pending reservations (Phase 4 payment-failure territory), API-route wiring, schema changes beyond the function itself

STRATEGY CHOSEN (and why):
- SELECT ... FOR UPDATE on the single categories row inside a database transaction
- supabase-js cannot open transactions or take locks: every .from() call is an independent PostgREST request, so app-level sequencing of read-minimum + insert is NOT atomic. The critical section therefore lives in a PL/pgSQL function invoked via supabase.rpc() through the service client
- Narrowest correct lock: one row per category -> same-category bids serialize; different categories lock different rows and proceed concurrently; lock held only for the transaction duration, released automatically
- Rejected alternatives: advisory locks (discouraged casually; key-collision subtleties), SERIALIZABLE isolation (broader contention + retry machinery for no benefit here), unique partial index on pending bids (that is reservation policy closer to Task 3.7 and rejects rather than serializes)

RESERVATION CORRECTNESS (the subtle part):
A row lock alone does NOT suffice: transaction T2 unblocked after T1 commits would recompute the minimum from PAID bids only and still derive the same amount slot (T1's bid is pending, not paid). Inside the lock the authoritative floor therefore accounts for pending reservations too:
  - no paid AND no pending bids -> minimum = categories.starting_bid
  - otherwise                   -> minimum = greatest(paid_max, pending_max) + increment
Consequence: simultaneous same-category bids receive strictly increasing reserved slots; abandoned pendings hold their slot until Phase 4 expiry/failure handling addresses them (documented interaction, not silently ignored).

SECURITY MODEL PRESERVED:
- Function is SECURITY DEFINER with pinned search_path=public (definer context bypasses RLS), so it re-checks is_active and recomputes the minimum authoritatively itself - caller input is never trusted even from our own server code path
- Postgres grants EXECUTE to PUBLIC by default: revoked from public, anon, authenticated; granted ONLY to service_role. Public clients still never see the service-role key; anon can neither call the RPC nor write rows under RLS
- Pre-validation (validateCategory + validateBidAmount from Tasks 3.4/3.3) kept as fast-fail UX; the in-lock recheck remains the source of truth

ERROR CONTRACT (stable for Task 4.1):
- Same CreatePendingBidResult union as Task 3.5; new internal mapping only:
  'bid_error:category_not_found' -> reason category_not_found
  'bid_error:amount_below_minimum:<min>' -> reason amount_below_minimum with parsed minimumBid echoed
  anything else -> descriptive thrown Error (infrastructure failure)
