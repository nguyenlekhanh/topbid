TASK ID: 5.7

TITLE: Connection/reconnection handling
STATUS: completed

OBJECTIVE:
Handle Supabase Realtime connection failures and recovery for the bids subscription: deduplicate outage signals, detect genuine recovery, and ensure consumers resync authoritative data after a reconnect so changes missed while disconnected are not silently lost.

REQUIREMENT DERIVATION:
PROJECT_PLAN.md specifies "5.7 | Connection/reconnection handling | 5.6". The authoritative-data model (realtime payloads are signals; DB queries are truth) means recovery is handled by triggering an authoritative refetch on reconnect - not by trusting buffered payloads or maintaining client-side event replay.

DESIGN:
- src/lib/realtime.ts now translates raw channel lifecycle statuses into a deduplicated RealtimeConnectionStatus signal ('connected' | 'disconnected') exposed via an optional onStatusChange callback on subscribeToBidChanges
- Status mapping per installed supabase-js API:
  * CHANNEL_ERROR / TIMED_OUT / CLOSED -> 'disconnected' (emitted ONCE per outage via a hasDisconnected guard; repeated failures while down do not re-emit)
  * SUBSCRIBED after such an outage -> 'connected' (recovery); the INITIAL SUBSCRIBED emits nothing because consumers already perform their own initial fetch
- Recovery semantics: trackers treat 'connected' as a coalesced authoritative refetch trigger - single implementation per tracker, no duplicated reconnection logic in components, and changes missed while offline are recovered by the fresh query rather than trusting anything received during the outage
- Unsubscribe behavior unchanged: removeChannel detaches change AND status handlers (fake/test parity), so no duplicate subscriptions or stale listeners can accumulate across reconnect cycles

SCOPE:
- src/lib/realtime.ts - status mapping + dedup + optional onStatusChange parameter
- src/lib/highest-bid-tracker.ts / leaderboard-tracker.ts / recent-bids-tracker.ts - options gain optional onConnectionChange, forwarded to subscribe; 'connected' triggers each tracker's existing coalesced refetch
- No UI changes required (recovery is data-level; visible offline banners would be polish beyond the task)
