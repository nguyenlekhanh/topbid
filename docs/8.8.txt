TASK ID: 8.8
PHASE: 8
TITLE: Audit logs
STATUS: completed

OBJECTIVE:
Add an immutable first-party audit trail for administrative mutations - who, what, on what target, when, with structured context - plus a bounded newest-first admin read surface. No analytics/event-bus/third-party providers; no Phase 9+ scope.

ARCHITECTURE:
- migration 20260823000021 creates audit_logs: identity PK; actor_user_id uuid NOT NULL (verified Supabase Auth id from getAdminContext - never a client claim); actor_email snapshot (trail stays self-describing even if the auth user is later removed); action CHECK allow-list covering exactly the seven Phase-8 mutation types (category.create|update|activate|deactivate, payment.refund, banned_email.ban|unban); target_type/target_id from server-side mutation results; detail jsonb for small structured context; created_at server-generated. Index idx_audit_logs_created_at DESC.
- Immutability: RLS enabled with ZERO policies (anon/authenticated fully blocked); only service-role inserts via writeAuditLog exist and no update/delete paths are present anywhere.

ATOMICITY / FAILURE MODEL:
Existing Phase-8 mutations are single-statement writes outside shared transactions, so audit inserts are BEST-EFFORT immediately after a successful mutation: writeAuditLog never throws, failures are logged loudly and reported as false, and business results are unaffected. This is documented rather than rewriting each write into a new RPC. Failed validations/refusals record nothing (no false-success audit entries); idempotent no-op outcomes ARE recorded with their outcome (e.g. already_refunded/duplicate), matching 4.x webhook conventions without inventing new dedup rules.

ACTOR/ACTION/TARGET SEMANTICS:
- Actor identity comes exclusively from getAdminContext() (Task 8.1 boundary extended to also expose the admin email in the same pass) - client claims are never trusted
- Allow-listed action names only; unknown actions rejected before any query
- Read path readAuditLogs() is itself guard-gated fail-closed; unauthorized callers get zero DB access

INTEGRATION POINTS:
- admin-category-management.ts: category.create / category.update / category.activate / category.deactivate audited after success (target = category/<server-generated id or updated id>, detail = slug or changed-field list)
- admin-refunds.ts: payment.refund audited for refunded / already_refunded(+duplicate) / refund_submitted outcomes (target = bid/<bidId>, detail = outcome + stripe refund id)
- email-bans.ts: banned_email.ban / banned_email.unban audited (target = banned_email/<canonical>)
- /admin/audit-logs page renders the newest-first trail (actor email, action, target, truncated detail) behind the same authorization gate
