STOP CONDITIONS (halt launch/immediately roll back if ANY occurs):
  - Migration verification (Step 1c/d) fails
  - Webhook signature verification fails (Stripe shows non-200 or app logs signature
    failures)
  - The LIVE payment does not reconcile (bid stays pending past webhook retry window,
    or ledger/state-machine invariant breaks)
  - Production URL mismatch (success/cancel/unsubscribe/canonical URLs show any other
    origin)
  - Secrets appear in client output (bundle scan, browser devtools, error events)
  - Admin authorization fails open or leaks account existence
  - Refund does not converge (db_pending never reconciles via webhook)
  - Rate limits/RLS/ban enforcement behave differently than the suites prove

ROLLBACK GUIDANCE (no invented infrastructure):
- APPLICATION: Vercel Deployments -> promote/roll back to the previous known-good
  deployment (instant, no data impact). For a code-level revert: git revert the commit
  on main and push - a new deployment is created automatically. Never force-push main.
- DATABASE: DO NOT attempt destructive rollback. The schema is migration-forward-only
  and payment state transitions are append/transition-only (ledger + status machine);
  rows are financial records. Corrective actions are new forward migrations only, with
  the Task 4.x RPCs as the ONLY writers of payment state.
- PAYMENTS ENTRY: if payments must be halted, disable the webhook endpoint or pause
  payments in the Stripe Dashboard (provider-side switch; no code change needed).
  In-flight sessions may still complete - reconcile them through the normal webhook
  path once re-enabled; the ledger keeps everything exactly-once.
- DOMAIN: reverting NEXT_PUBLIC_APP_URL/re-pointing DNS is safe post-launch because
  every absolute URL derives from that one variable (requires redeploy).
- LEDGER INTEGRITY during rollback is preserved by design: processed_webhook_events +
  bid-row transitions live in the production database and are independent of any
  application deployment version.
