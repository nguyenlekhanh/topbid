TASK ID: 4.9
PHASE: 4
TITLE: Idempotent webhook handling
STATUS: completed

OBJECTIVE:
Make Stripe webhook event processing idempotent using Stripe's authoritative event ID, with the database uniqueness constraint as the race-safe final arbiter - so duplicate/replayed deliveries can never duplicate business effects, and failed processing stays retryable.

MECHANISM (each design question answered explicitly):
- Ledger schema: new table processed_webhook_events(event_id text PRIMARY KEY, type text NOT NULL, processed_at timestamptz NOT NULL DEFAULT now()). Stripe's event.id is the identity; the PRIMARY KEY is the uniqueness rule. No payload storage (minimal).
- Claim placement: claim INSERT and business effect run in the SAME transaction via wrapper RPC process_checkout_completed_event - a claim without its effect would permanently swallow retries if processing failed
- Duplicate behavior: unique_violation on the claim -> outcome 'duplicate' -> endpoint answers 200 {received:'true', duplicate:'true'} so Stripe stops retrying; first delivery's effect stands
- Failed processing: conversion anomalies ('bid_not_found','invalid_state','session_mismatch') RAISE inside the RPC -> the whole transaction rolls back INCLUDING the claim -> the event remains retryable and is answered 500
- Atomicity/race-safety: concurrent deliveries serialize on the PK; no application SELECT-then-INSERT anywhere
- Unsupported events: still acknowledged WITHOUT ledger entries (no business effects to dedupe; Task 4.5 semantics unchanged)
- No client-controlled bypass: event.id/type are taken from the constructEvent-verified payload only, after Tasks 4.6+4.7

SCOPE:
