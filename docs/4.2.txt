TASK ID: 4.2
PHASE: 4
TITLE: Attach category/bid metadata
STATUS: completed

OBJECTIVE:
Link the Stripe Checkout Session to its pending bid using the plan-required category/bid metadata mechanism, and persist stripe_session_id onto the authoritative bid record so webhook handling can resolve the bid by session identity.

LINKAGE MECHANISM:
- client_reference_id = bid.id (Stripe's canonical field for carrying a merchant-side reference)
- metadata = { bid_id, category_id } - exactly the "category/bid metadata" named by the task; both values come from the DB-validated Bid row, never from client input
- stripe_session_id persisted on the bids row afterwards via RPC, enabling lookup through idx_bids_stripe_session (Task 2.3) during Tasks 4.5+/4.8

SCOPE:
- New migration supabase/migrations/20260823000009_attach_stripe_session_function.sql - attach_stripe_session(p_bid_id uuid, p_stripe_session_id text) returns boolean
  * UPDATE ... WHERE id = p_bid_id AND status = 'pending' AND stripe_session_id IS NULL (attach-once guard)
  * unique_violation handler raises the established 'bid_error:duplicate_transaction' protocol message (UNIQUE(stripe_session_id) makes concurrent cross-bid attaches impossible - race-safe)
  * returns true when attached; false when bid missing/not-pending/already-attached
  * SECURITY DEFINER + pinned search_path; EXECUTE revoked from public/anon/authenticated, granted ONLY to service_role (RLS untouched)
- src/lib/checkout.ts - session creation now passes client_reference_id + metadata; after creation the session identifier is attached via the service-role RPC; result contract gains additive stripeSessionId field; attachment failures throw descriptive errors
- src/lib/checkout.test.ts - happy path asserts exact create params incl. linkage fields and the attach RPC invocation; two new failure-path tests (ineligible attach, attach DB error); suite now 8 tests

OUT OF SCOPE:
- Webhook endpoint/signature verification/payment confirmation (Tasks 4.5-4.9), success/cancel pages (4.3/4.4), refunds, rate limiting; no changes to completed tasks' logic

PRESERVED BEHAVIOR:
- Task 3.5 authoritative validation unchanged (bid created first, pricing from DB row only)
- Task 3.6 concurrency RPC untouched; reservation semantics unaffected
- Task 3.7 duplicate semantics preserved and reinforced: NULL -> session-id transition is one-way at the DB boundary; a second attach of any identifier to another bid hits UNIQUE(stripe_session_id)
- RLS/security model intact; service credentials confined to server modules

CRASH-WINDOW NOTE (documented honestly):
If the process dies between session creation and attachment, the bid remains pending with a NULL session id while the session still references it via client_reference_id/metadata, so Phase 4 confirmation can still resolve it. This mirrors the already-documented abandoned-reservation behavior from Task 3.6.
