TRUST-FLOW DIAGRAM (verified end-to-end)
============================================================

POST /api/webhooks/stripe
  -> request.text() [RAW body, never parsed/re-serialized]
  -> headers.get('stripe-signature')
  -> processStripeWebhook(payload, signature)
       -> STRIPE_WEBHOOK_SECRET presence check (500 if missing)
       -> payload/signature non-empty check (400 if missing)
       -> stripe.webhooks.constructEvent(payload, sig, secret, 300s tolerance)
            FAILS -> 400 {error:'Invalid signature'} [no business logic reached]
       -> event.type allow-list check (3 types; others ignored w/ 200)
       -> handleCheckoutSessionCompleted / handleChargeRefunded / handleAsyncPaymentFailed
            -> verifyCheckoutSessionPaid: stripe.checkout.sessions.retrieve (authoritative re-retrieval)
            -> payment_status === 'paid' check
            -> client_reference_id/metadata.bid_id consistency check
            -> processVerifiedEvent -> RPC process_checkout_completed_event
                 -> ledger claim (processed_webhook_events PK = event.id)
                 -> row lock (SELECT FOR UPDATE on bids)
                 -> state transition (pending->paid only)
                 -> atomic insert+transition in one transaction
            -> deliverOutbidNotification (best-effort email, independent of payment correctness)
       -> HTTP response (200/400/500)

1. ENDPOINT BOUNDARY FINDINGS:
- Only POST is exported; Next.js returns 405 for all other methods automatically
- Raw body via request.text() - never parsed or re-serialized before signature verification
- stripe-signature header extracted via standard API
- Signature verification happens FIRST - no business logic executes until it passes
- Invalid/missing signatures return 400 immediately with generic error message
- Malformed signed payloads cause constructEvent to throw -> 400 (SDK handles JSON parsing internally after verification)
- Content-Type is not checked because signature verification operates on raw bytes regardless of encoding
- Request size bounded by platform limits (Vercel ~4.5MB) - far larger than any legitimate Stripe webhook

2. SIGNATURE/REPLAY FINDINGS:
- Stripe SDK constructEvent used as-is with explicit 300s tolerance (matching Stripe's default); implementation does NOT manually weaken or bypass verification
- Webhook signing secret consumed exclusively inside constructEvent call; never logged, serialized, or exposed
- Replay protection: SDK rejects timestamps older than 300s; ledger PK(event.id) absorbs redeliveries within the window
- Three replay categories distinguished:
  (a) Cryptographically invalid replay -> 400 (signature fails)
  (b) Valid Stripe event replay within tolerance -> 200 + ledger 'duplicate' outcome (no business effect)
  (c) Duplicate delivery after successful processing -> 200 + 'duplicate' (idempotent no-op)
  (d) Retry after transient processing failure (500) -> ledger claim persists through rollback; next delivery resolves as already_paid/duplicate

3. EVENT ALLOW-LIST/DISPATCH FINDINGS:
- Exactly 3 types accepted: checkout.session.completed, checkout.session.async_payment_failed, charge.refunded
- Unknown types acknowledged with 200 {received:true, ignored:true} - cannot mutate payment state
- Dispatch occurs only AFTER constructEvent succeeds - unsigned/tampered events never reach handlers
- Each accepted type reaches exactly one handler (checkout/completed, refunded, async_payment_failed)
- attacker-controlled event.type cannot select arbitrary behavior: the Set membership check constrains dispatch to 3 known strings

4. EVENT AUTHORITY FINDINGS:
- event.id: used solely as ledger dedup key; not a bid/payment identifier
- event.type: used solely for handler routing; cannot select arbitrary code paths beyond the 3 allowed handlers
- checkout session ID: extracted from event body, used as LOOKUP KEY for authoritative Stripe API re-retrieval - the retrieved session's fields are the authority, not the event body's
- payment intent ID: extracted from verified Stripe API response (not event body), persisted during conversion
- bid ID/client_reference_id/metadata.bid_id: consistency-checked against each other; mismatch rejected; used as lookup key for RPC, never trusted as authorization
- refund ID (charge.id): used as lookup key for authoritative charges.retrieve requiring refunded=true
- Event metadata CANNOT directly mark a bid paid: conversion requires verifyCheckoutSessionPaid to succeed first, which queries Stripe's API independently

5. DUPLICATE/REPLAY SCENARIO RESULTS:
A. Same valid event delivered twice -> ledger 'duplicate', no business effect
B. Same event many times -> same as A; bounded by Stripe retry policy (~3 days)
C. After 200 response -> Stripe stops retrying; subsequent manual redelivery hits ledger duplicate
D. After 500 response -> Stripe retries; ledger claim persists through rollback; next attempt resolves as duplicate/already_paid
E. Two different events for same payment -> each gets own ledger entry; second transition resolves as already_paid/already_refunded
F. Missing bid -> bid_not_found -> 500 (Stripe retries, then gives up)
G. Mismatched session/bid -> session_mismatch -> 500 (loud failure, monitoring surfaces)
H. Mismatched PI/bid -> invalid_state or session_mismatch -> 500
I. Unexpected metadata -> consistency checks reject; no mutation occurs
J. Invalid signature with valid-looking payload -> 400, no processing whatsoever

6. FAILURE SEMANTICS / HTTP STATUS:
- Signature verification failure -> 400 (Stripe does NOT retry authentication failures)
- Event parsing failure -> caught by constructEvent -> 400
- DB lookup failure (verifyCheckoutSessionPaid throw) -> 500 (Stripe retries)
- Authoritative RPC failure -> 500 (Stripe retries; ledger claim rolled back)
- Notification email transport-unconfirmed failure -> 500 (intentional: Stripe redelivery retries the email)
- Already-processed event received -> 200 + duplicate flag (Stripe stops retrying)

7. LEDGER/RPC SECURITY:
- processed_webhook_events: event_id TEXT PRIMARY KEY (race-safe arbiter)
- All payment RPCs: SECURITY DEFINER + pinned search_path = public
- EXECUTE revoked from public/anon/authenticated; granted ONLY to service_role
- Row locking: SELECT ... FOR UPDATE on bids table in convert/refund transitions
- Atomic: ledger insert + state change in one INSERT...EXCEPTION block
- Rollback: anomalies raise inside RPC, rolling back BOTH claim AND effect
- Attacker CANNOT call payment-transition RPCs directly: EXECUTE revoked from all non-service-role principals; service_role key is server-only environment variable

8. RESPONSE BEHAVIOR:
- Responses contain only stable flags: {received:'true'}, {received:'true',duplicate:'true'}, {received:'true',ignored:'true'}, {error:'Invalid signature'}, {error:'Webhook processing failed'}
- NO bid existence info, internal IDs, Stripe payload details, database errors, signing secrets, or email addresses revealed
- Response behavior is intentionally generic for attacker-controlled requests: identical 400 for all signature failures regardless of payload content

9. LOGGING/PRIVACY FINDINGS:
- No raw request body logged anywhere in webhook processing
- No signing secret logged or serialized
- No full Stripe object dumps; only specific identifiers (event_id, session_id, bid_id, refund_id) and error summaries
- No bidder PII in webhook logs (emails appear only in outbid-notification module which is separate)
- Log entries retain operational context (which event/session/outcome) without leaking sensitive data
