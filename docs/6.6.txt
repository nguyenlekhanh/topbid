TITLE: Unsubscribe handling
STATUS: completed

OBJECTIVE:
Allow outbid-notification recipients to opt out of future notifications without accounts (MVP constraint), enforce that opt-out server-side in the existing notification flow, and advertise unsubscription at the transport level.

REQUIREMENT DERIVATION:
PROJECT_PLAN.md specifies "6.6 | Unsubscribe handling | 6.5" - a single line. Architecture was derived from what exists: the project sends raw transactional emails via resend.emails.send() with NO Audiences/Contacts/suppression infrastructure, so provider-managed opt-out is unavailable; durable suppression state must therefore live in the application. This matches the prompt's success criterion ("a recipient who has unsubscribed must not receive future outbid notifications through this flow").

ARCHITECTURE CHOSEN:
Application-managed unsubscribe state keyed by recipient-specific capability tokens.
- token = HEX(HMAC-SHA256(UNSUBSCRIBE_SECRET, lowercased_email)) - deterministic per recipient; it is BOTH the URL token and the notification_unsubscribes PRIMARY KEY, so lookup-by-token resolves suppression directly
- Raw email addresses are NEVER stored in the unsubscribe table and NEVER appear in URLs (@-free)
- Tokens cannot be forged, guessed, or reused across recipients without UNSUBSCRIBE_SECRET (server-only, min 32 chars, lazy memoized validation like resend.ts)

SECURITY MODEL:
- No auth/accounts introduced; possession of a valid token = proof the link was issued to that recipient
- node:crypto HMAC (already used by the Stripe signature suite); shape validation requires exactly 64 lowercase hex chars before any DB access
- notification_unsubscribes has RLS enabled with ZERO policies - only the service role touches it
- The unsubscribe page renders AUTHORITATIVE state for a well-shaped token; malformed tokens get neutral copy leaking nothing about existence
- Only POST mutates (GET page renders) - email-scanner prefetch cannot unsubscribe anyone

SCOPE:
