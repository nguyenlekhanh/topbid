TASK ID: 8.5
PHASE: 8
TITLE: Payment management
STATUS: completed

OBJECTIVE:
Provide administrators a payment-centric oversight view - authoritative statuses, amounts, timestamps, and the Stripe identifiers needed to cross-reference the Stripe dashboard - as a READ-ONLY capability. The refund ACTION is explicitly Task 8.6 (PROJECT_PLAN.md: "8.6 | Refund action | 8.5"), so no mutation exists in this task.

PAYMENT-SAFETY ANALYSIS (performed before any code):
- Status transitions are owned exclusively by verified-webhook RPCs inside ledger transactions (Tasks 4.8-4.11): convert_pending_bid_to_paid / fail_pending_bid / refund_paid_bid behind process_checkout_completed_event + processed_webhook_events (event.id PK)
- Direct admin writes to bid.status/paid_at/stripe fields would create an alternate payment pipeline and were rejected outright
- Stripe-side initiation (refunds.create) belongs to Task 8.6; adding it here would violate the plan decomposition
- Therefore 8.5 ships as pure read-only oversight; zero Stripe API calls, zero mutations

WHAT THIS VIEW ADDS OVER TASK 8.4's BID LIST:
The AUTHORITATIVE PAYMENT IDENTIFIERS (Stripe Checkout Session id + PaymentIntent id) admins need for Stripe-dashboard cross-referencing, plus per-status counts across the read window.

DATA EXPOSURE (exact):
Shown: placed timestamp, category name, whole-dollar amount, colored status badge, stripe_session_id, stripe_payment_intent_id (mono/truncated cells), paid_at.
Excluded by design: bidder email, bidder display name, internal bid id, unsubscribe tokens, webhook payloads/signatures, any credentials. Column selection excludes personal fields at the query level AND rows pass through an explicit allow-list mapping.

QUERY MECHANISM:
listPaymentsForAdmin() in server-only src/lib/admin-payment-management.ts: getAdminAuthorization() gate -> service-role select of created_at/amount/status/paid_at/stripe_session_id/stripe_payment_intent_id/categories(name), ordered created_at DESC LIMIT 100 (bounded window). Per-status counts aggregated from the mapped rows. No caching (fresh every request).

IDEMPOTENCY / DUPLICATES:
Pure read - naturally repeatable, nothing to dedupe. No queues/retries/schedulers introduced.
